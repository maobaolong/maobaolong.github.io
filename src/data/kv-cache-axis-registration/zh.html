02 / 最初要解决的正确性问题

当 block 数是 2，shape 和 stride 无法判断哪个轴代表 K/V。

RBLN 有两种合法 view：自定义 kernel 使用 [B,2,H,1,N,D]；Triton 路径使用 [2,B,H,1,N,D]。当 B=2时，两者的 shape 和连续 strides 完全相同。探测器可以选一种解释，却无法恢复生产者的真实意图。

图 2 · 同一组物理数值，两种语义解释
Shape 和 stride 完全相同

示例取 H=1、N=2、D=1，标量值等于物理偏移。颜色表示声明的组件角色，并非字节中自带的信息。

Block 轴在前

BLOCKKVHEAD1STATEHEAD_DIM

K/V 轴在前

KVBLOCKHEAD1STATEHEAD_DIM

独立构造的标准输出先按组件，再按 block 和 state 排序。B=2 时，相同几何信息会得到不同的 K/V 序列。B=3 时这两种 shape 可区分，但任意 shape 仍不等于语义声明。

为什么仅测往返可能漏掉问题： 用错误解释存储，再用同样的错误解释恢复，仍可能还原原始 buffer。必须与独立构造的 K、V 预期序列比较，才能发现语义错误。

LMCache #5748 增加了两种 RBLN 格式的支持，修复了一项实际部署回归。即使这个探测修复已经存在，两个 block 时的歧义仍说明生产者契约很有价值。

03 / 先把容易混淆的概念分开

“Layout”其实涵盖三份不同的契约。

图 3 · 语义、地址、内容

1 · 轴语义：每个索引是什么意思？

BLOCKHEADSTATECONTENT

KVCacheTensorLayout.axes 描述张量的索引顺序，由本 PR 新增。它不按 stride 给轴排序，也不解释 CONTENT 内部的内容。

+

2 · 物理几何：字节实际放在哪里？

shape + stride + dtype + storage_offset + storage。现有的 KVCacheLayout 选择 LBHNC、LBNHC 等物理排列。一个 block 不一定是一整段紧密连续的内存。

+

3 · 内容／state 语义：这些字节存的是什么？

KVCacheSpec 以及 backend 契约定义 packing、head slot、量化、latent／循环状态内容，以及每个 state 对应多少 token。本 PR 不序列化所有这些信息。

名称这里的含义不能据此假设
KVCacheAxis.KV显式二选一轴：索引 0 是 K，索引 1 是 V。不是 cache 数量，也不是 MLA latent 的数量轴。
STATE ／逻辑维 N存储的位置或循环状态。一个 state 不一定对应一个原始 token。
CONTENT ／维 C每个 head slot、每个 state 的不透明 payload。不隐含 K/V 拆分方式或量化编码。
HEAD ／维 H对外 view 中的 head slot。不一定等于模型的 KV head 数量。
层名 key／cache group层名标识注册的张量；group 表达 cache 管理与 spec 的关联。Group 不是张量轴，也不必独占一份 allocation。
LMCache 内部格式消费者内部的语义解释与传输分派方式。它不是 vLLM 物理布局所使用的同一个枚举： KVCacheLayout。

04 / 轴含义相同，内存顺序可以不同

标准 view 始终是 BHNC，stride 则可以变化。

公共 allocator 先创建逻辑形状为 [L,B,H,N,C] 的 view，再逐层选取得到 [B,H,N,C]。物理排列和 page padding 由 stride、offset 表达，不需要重命名对外索引的语义。

图 4 · 同一种索引契约，两种物理顺序

LBHNC

同一层、同一 block 内，head 排在 state 前。

H0 N0H0 N1H1 N0H1 N1
cache[b,h,n,c]

LBNHC

同一层、同一 block 内，state 排在 head 前。

N0 H0N0 H1N1 H0N1 H1
cache[b,h,n,c]
示例每层 shape每层 stride，单位为元素轴元组
LBHNC[8,4,16,128][8192,2048,128,1](BLOCK,HEAD,STATE,CONTENT)
LBNHC[8,4,16,128][8192,128,512,1]

彩色条只示意 H/N 单元；数值表取 B=8、H=4、N=16、C=128。这不代表所有 backend 都支持两种顺序。

address(b,h,n,c) = storage_base + element_size × (
    storage_offset + b·stride_B + h·stride_H + n·stride_N + c·stride_C
)

张量的 stride 和 storage_offset 以元素为单位；allocator 规划可能用字节 stride，必须显式换算。轴 metadata 提供 B/H/N/C 的含义，不提供地址公式里的数值。

10 / Size 为 1 的维度，不自动等于 KV 维度
MLA 的标准 view 没有独立的 K/V 选择轴。


描述符里的 KV 角色表示可分别寻址的两个组件，先 K 后 V。MLA 的共享 latent 不应该被标成只有一个元素的 K/V 选择轴。 MLAAttentionSpec 设置 head_size_v=0；内容如何解释仍由 spec 决定。


图 10 · 三种合法的 MLA 声明
标准 view
[B,1,N,C]
BLOCKHEADSTATECONTENT
Size 为 1 的维度代表 head slot，保留 HEAD 角色。
自定义 squeeze 后的 view
[B,N,C]
BLOCKSTATECONTENT
描述符不强制要求 head 轴或 K/V 轴。
带额外占位维的自定义 view
[1,B,N,C]
SINGLETONBLOCKSTATECONTENT
真正的占位维才使用 SINGLETON；有语义的轴保留其角色。


不合法的声明： 把 [1,B,N,C] 描述为 (KV,BLOCK,STATE,CONTENT) 会抛出 ValueError。单个元素并未说明它是 K、V 还是共享 latent。放宽 size 检查只会引入歧义，不会因此编码出 MLA 的语义。


validate_shape 检查 rank、KV 必须为 2、SINGLETON 必须为 1。构造描述符时还会拒绝除 SINGLETON 外重复的命名角色。这些检查不能证明声明真实：相同大小的轴仍可能标错。正确性首先依赖生产者已知的 view 契约。

13 / 不传声明，会丢失什么
错误的轴解释，可能最终变成错误的字节选择。


图 13 · 可能的失效链，不是已确认的生产事故
无语义标签的 view消费者只看到 shape 与 stride。
→

→
几何解释错误Block／KV 角色或组件拆分错误。
→
传输了错误的字节标准 chunk 中可能出现错配的 K/V 序列。


可见的拒绝
生产者的新布局可能被判为不支持。LMCache #5748 对 RBLN block-first 的支持修复过一项具体集成回归。
静默的语义歧义
大小相同的轴可以通过 shape 和越界检查。独立标准值测试展示了这种风险；本文没有声称已观察到生产模型输出错误。
维护耦合
生产者每次改 shape，都可能要求消费者新增启发式规则，即使生产者本来就知道语义。


并非所有只传张量的集成都不安全。现有 spec-aware 契约可以非常精确，很多布局也没有歧义。问题在于：几何信息或 backend 名称并不总能充当完整语义契约。

事件张量变化描述符／上下文应如何更新
Permute[B,H,N,C] → [B,N,H,C]轴元组同步置换为 (BLOCK,STATE,HEAD,CONTENT)。
Squeeze 一个 head slot[B,1,N,C] → [B,N,C]从暴露的 view 声明里移除 HEAD，不能仍保留四维描述符。
共享层别名新的层名指向同一张量。在别名 key 下复制目标描述符，两套 runner 已接通。
组件拆分／reshape一份 payload 拆成多个 view，或合并维度。描述新的 view 角色和组件身份；仅置换轴不一定足够。更完整的 schema 仍是后续工作。
重分配／恢复新的 storage 或新的 view。用匹配的新张量／描述符重新注册，不能依赖旧地址或过期 metadata。
跨进程交接不能原样跨进程传递 Python 对象。序列化为消费者理解的带版本契约；保留 dtype／spec／state 上下文，并拒绝不支持的版本。


只有后续 adapter 保留语义，最初那次声明才有意义。张量被重新解释、squeeze 或 regroup 后仍沿用旧轴标签，会重新制造同样的问题。
