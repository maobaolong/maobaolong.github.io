02 / 最初要解决的正确性问题

当 block 数是 2，shape 和 stride 无法判断哪个轴代表 K/V。

RBLN 有两种合法 view：自定义 kernel 使用 [B,2,H,1,N,D]；Triton 路径使用 [2,B,H,1,N,D]。当 B=2时，两者的 shape 和连续 strides 完全相同。探测器可以选一种解释，却无法恢复生产者的真实意图。

图 2 · 同一组物理数值，两种语义解释
Shape 和 stride 完全相同

示例取 H=1、N=2、D=1，标量值等于物理偏移。颜色表示声明的组件角色，并非字节中自带的信息。

Block 轴在前

BLOCKKVHEAD1STATEHEAD_DIM

K/V 轴在前

KVBLOCKHEAD1STATEHEAD_DIM

独立构造的标准输出先按组件，再按 block 和 state 排序。B=2 时，相同几何信息会得到不同的 K/V 序列。B=3 时这两种 shape 可区分，但任意 shape 仍不等于语义声明。

为什么仅测往返可能漏掉问题： 用错误解释存储，再用同样的错误解释恢复，仍可能还原原始 buffer。必须与独立构造的 K、V 预期序列比较，才能发现语义错误。

LMCache #5748 增加了两种 RBLN 格式的支持，修复了一项实际部署回归。即使这个探测修复已经存在，两个 block 时的歧义仍说明生产者契约很有价值。

03 / 先把容易混淆的概念分开

“Layout”其实涵盖三份不同的契约。

图 3 · 语义、地址、内容

1 · 轴语义：每个索引是什么意思？

BLOCKHEADSTATECONTENT

KVCacheTensorLayout.axes 描述张量的索引顺序，由本 PR 新增。它不按 stride 给轴排序，也不解释 CONTENT 内部的内容。

+

2 · 物理几何：字节实际放在哪里？

shape + stride + dtype + storage_offset + storage。现有的 KVCacheLayout 选择 LBHNC、LBNHC 等物理排列。一个 block 不一定是一整段紧密连续的内存。

+

3 · 内容／state 语义：这些字节存的是什么？

KVCacheSpec 以及 backend 契约定义 packing、head slot、量化、latent／循环状态内容，以及每个 state 对应多少 token。本 PR 不序列化所有这些信息。

名称这里的含义不能据此假设
KVCacheAxis.KV显式二选一轴：索引 0 是 K，索引 1 是 V。不是 cache 数量，也不是 MLA latent 的数量轴。
STATE ／逻辑维 N存储的位置或循环状态。一个 state 不一定对应一个原始 token。
CONTENT ／维 C每个 head slot、每个 state 的不透明 payload。不隐含 K/V 拆分方式或量化编码。
HEAD ／维 H对外 view 中的 head slot。不一定等于模型的 KV head 数量。
层名 key／cache group层名标识注册的张量；group 表达 cache 管理与 spec 的关联。Group 不是张量轴，也不必独占一份 allocation。
LMCache 内部格式消费者内部的语义解释与传输分派方式。它不是 vLLM 物理布局所使用的同一个枚举： KVCacheLayout。

04 / 轴含义相同，内存顺序可以不同

标准 view 始终是 BHNC，stride 则可以变化。

公共 allocator 先创建逻辑形状为 [L,B,H,N,C] 的 view，再逐层选取得到 [B,H,N,C]。物理排列和 page padding 由 stride、offset 表达，不需要重命名对外索引的语义。

图 4 · 同一种索引契约，两种物理顺序

LBHNC

同一层、同一 block 内，head 排在 state 前。

H0 N0H0 N1H1 N0H1 N1
cache[b,h,n,c]

LBNHC

同一层、同一 block 内，state 排在 head 前。

N0 H0N0 H1N1 H0N1 H1
cache[b,h,n,c]
示例每层 shape每层 stride，单位为元素轴元组
LBHNC[8,4,16,128][8192,2048,128,1](BLOCK,HEAD,STATE,CONTENT)
LBNHC[8,4,16,128][8192,128,512,1]

彩色条只示意 H/N 单元；数值表取 B=8、H=4、N=16、C=128。这不代表所有 backend 都支持两种顺序。

address(b,h,n,c) = storage_base + element_size × (
    storage_offset + b·stride_B + h·stride_H + n·stride_N + c·stride_C
)

张量的 stride 和 storage_offset 以元素为单位；allocator 规划可能用字节 stride，必须显式换算。轴 metadata 提供 B/H/N/C 的含义，不提供地址公式里的数值。

HiSparse 是 MRV2 内部的一条路径，不是与 MRV1、MRV2 并列的第三版执行器。公共 view 创建函数为 device／host view 生成轴声明；自管理的 raw storage 仍保持未指定。




什么时候选择 MRV1 或 MRV2？


下面按本文固定源码版本的优先级说明。Out-of-tree worker 可以覆写执行器构造逻辑，因此这不是适用于所有 device 的通用选择表。


条件，按优先级排列结果


配置了 HiSparse。必须 MRV2；显式设置 VLLM_USE_V2_MODEL_RUNNER=0 会报错。


配置了 watermarking。必须 MRV2，即使显式设为 0 也会被覆盖。


其余情况下，显式设置 VLLM_USE_V2_MODEL_RUNNER=1。请求 MRV2，仍需通过兼容检查；GPU worker 会拒绝缺少 Triton 的 MRV2 配置。


其余情况下，显式设置 VLLM_USE_V2_MODEL_RUNNER=0。请求 MRV1，仍需通过 MRV1 自身的功能兼容检查。


没有显式设置，且实际平台缺少 Triton。回退到 MRV1。


没有显式设置，且配置命中了 MRV2 尚不支持的功能。回退到 MRV1。


没有显式设置，也不满足以上回退条件。使用 MRV2。




这个版本中，MRV2 的限制示例包括 external_launcher 搭配 pipeline parallel、suffix／custom_class speculative 方法，以及 draft／target 词表不同的配置。支持范围会随版本变化，环境变量也不保证任意配置都能运行，应以对应版本的检查为准。


HiSparse 到底做什么？


HiSparse 是面向稀疏 MLA 的实验性、本地 KV offload 方案。稀疏 attention 每步只选取一部分历史位置，因此可以把历史 KV 保存在 pinned CPU 内存，GPU 使用 resident page 和热点行缓存，以 host 内存与数据传输为代价，降低历史 KV 的 GPU 显存占用。


本步选中的 top-k 历史位置
          ↓
GPU resident page 命中？── 是 → 使用驻留行
          ↓ 否
GPU hot row 命中？──────── 是 → 使用热点缓存行
          ↓ 否
从 pinned CPU 内存补入 GPU hot cache


融合的 GPU resolver 依次检查 resident page、hot row 和 host 内存。Indexer KV 有独立的管理方式；启用 HiSparse 不等于给模型的每个 KV group 都自动创建一份 CPU 副本。


什么时候启用 HiSparse？


直接配置 HiSparseConnector，或通过 MultiConnector 包含它时，会推导出默认 hisparse_config。Connector 提供 host_pool_gib 容量，HiSparseConfig 用来调节 GPU hot buffer 等字段。仍需一份完整且受支持的配置，显存不足本身不会自动开启 HiSparse。


此版本的主要约束：NVIDIA CUDA、MRV2，以及带 index_topk 的 DSA 模型。目前不支持 pipeline parallel 和 decode context parallel。单独的 cudagraph_mode=FULL 会被拒绝；默认的 FULL_AND_PIECEWISE 仍可以为 decode 捕获 full graph。这些是代码里的兼容条件，不代表本 PR 做过相应硬件验证。


HiSparseConnector 管理本地 host／GPU 驻留状态，可以通过 MultiConnector 与 P/D 或其它 offload connector 组合。它的职责与后文尚待实现的 LMCache adapter／MP 接入不同。


这与 #63699 的关系：普通 MRV2 分配和 HiSparse 的 host／device 分配，都必须把实际注册 view 的匹配轴声明传到 connector。本 PR 接通这些 metadata 路径，并不负责选择执行器或启用 HiSparse。Allocator 原有返回类型不变，共享层继承目标描述符，raw buffer 不会被凭空标为 BHNC。

10 / Size 为 1 的维度，不自动等于 KV 维度
MLA 的标准 view 没有独立的 K/V 选择轴。


描述符里的 KV 角色表示可分别寻址的两个组件，先 K 后 V。MLA 的共享 latent 不应该被标成只有一个元素的 K/V 选择轴。 MLAAttentionSpec 设置 head_size_v=0；内容如何解释仍由 spec 决定。


图 10 · 三种合法的 MLA 声明
标准 view
[B,1,N,C]
BLOCKHEADSTATECONTENT
Size 为 1 的维度代表 head slot，保留 HEAD 角色。
自定义 squeeze 后的 view
[B,N,C]
BLOCKSTATECONTENT
描述符不强制要求 head 轴或 K/V 轴。
带额外占位维的自定义 view
[1,B,N,C]
SINGLETONBLOCKSTATECONTENT
真正的占位维才使用 SINGLETON；有语义的轴保留其角色。


不合法的声明： 把 [1,B,N,C] 描述为 (KV,BLOCK,STATE,CONTENT) 会抛出 ValueError。单个元素并未说明它是 K、V 还是共享 latent。放宽 size 检查只会引入歧义，不会因此编码出 MLA 的语义。


validate_shape 检查 rank、KV 必须为 2、SINGLETON 必须为 1。构造描述符时还会拒绝除 SINGLETON 外重复的命名角色。这些检查不能证明声明真实：相同大小的轴仍可能标错。正确性首先依赖生产者已知的 view 契约。

14 / Metadata 要跟随 view 的生命周期

图 14 · 这些变换都需要同步语义
事件张量变化描述符／上下文应如何更新
Permute[B,H,N,C] → [B,N,H,C]轴元组同步置换为 (BLOCK,STATE,HEAD,CONTENT)。
Squeeze 一个 head slot[B,1,N,C] → [B,N,C]从暴露的 view 声明里移除 HEAD，不能仍保留四维描述符。

组件拆分／reshape一份 payload 拆成多个 view，或合并维度。描述新的 view 角色和组件身份；仅置换轴不一定足够。更完整的 schema 仍是后续工作。
重分配／恢复新的 storage 或新的 view。用匹配的新张量／描述符重新注册，不能依赖旧地址或过期 metadata。
跨进程交接不能原样跨进程传递 Python 对象。序列化为消费者理解的带版本契约；保留 dtype／spec／state 上下文，并拒绝不支持的版本。


只有后续 adapter 保留语义，最初那次声明才有意义。张量被重新解释、squeeze 或 regroup 后仍沿用旧轴标签，会重新制造同样的问题。

    layout = KVCacheTensorLayout(

test_allocator_views_and_aliases_keep_their_values 展开成 8 个用例：KVCacheLayout 的 6 个成员，加上 LBHNC、BLHNC 的 padded 版本。这里真正调用 compute_layout_strides 和 allocate_kv_cache，没有伪造分配结果；两个层共用 backing allocation，却有各自的 view。

    + [(KVCacheLayout.LBHNC, True), (KVCacheLayout.BLHNC, True)],

def test_allocator_views_and_aliases_keep_their_values(
    make_connector, physical_layout, padded

    """Registration describes indexing order while preserving real strides."""
    spec = FullAttentionSpec(
        block_size=4,
        num_kv_heads=2,
        head_size=2,
        dtype=torch.float32,
        page_size_padded=144 if padded else None,

        num_blocks=nb,
        kv_cache_tensors=[
            KVCacheTensor(
                size=nb * nl * spec.page_size_bytes,
                layers=["first", "second"],
                layer_stride=strides[0],
                block_stride=strides[1],
            )
        ],
        kv_cache_groups=[
            KVCacheGroupSpec(
                ["first", "second"],
                UniformTypeKVCacheSpecs(
                    block_size=4, kv_cache_specs={"first": spec, "second": spec}
                ),
            )
        ],
    )

    assert set(consumer.layouts) == set(caches)

    layout = consumer.layouts["first"]
    index = tuple(
        {Axis.BLOCK: 1, Axis.HEAD: 0, Axis.STATE: 2, Axis.CONTENT: 3}[axis]
        for axis in layout.axes
    )
    assert consumer.registered_caches["alias"][index].item() == 43
    assert torch.all(caches["second"] == -1)

3. 描述符不合法时，要在旧注册函数产生副作用之前失败。

pytest.raises(ValueError, match=message) 同时检查异常类型和错误类别；之后检查所有 child 都没有 registered_caches 属性，证明本 fixture 中旧 hook 尚未执行。这里第一个 child 继承了基类校验，所以它先拒绝，再停止 MultiConnector 的循环。这个断言不能推广成“任意自定义 child 都有事务回滚”；绕过基类校验的 override 不在这个测试的保证范围内。

4. 一个不存在的层名，不能凭空带着描述符混进注册。
test_unknown_layer_descriptor_is_rejected 使用空 tensor 字典，却给出 missing 的轴声明。预期是带 unregistered layer 信息的 ValueError。这防止 tensor map 与 layout map 的 key 集合失配，比如模型重建后残留了上一次的层名。
它检查的是“描述符不能指向不存在的 tensor”，并不要求每个 tensor 都必须有描述符；后者恰恰由第 6 项测试允许缺省。

5. 重复的语义轴在构造描述符时就拒绝。
test_rejects_duplicate_semantic_axes 直接构造 (BLOCK,BLOCK)，在进入 connector 前就应抛出带 unique 的 ValueError。否则 axis_index(BLOCK) 只能返回第一个位置，消费者会悄悄忽略另一个“BLOCK”。

6. 没有声明就是 unspecified，不能自动补一个“看起来合理”的布局。
test_missing_descriptors_stay_unspecified 建立一个带 HiSparse raw spec、但 kv_cache_tensors=[] 的配置。allocator 因为没有 allocation record 而返回空字典，输出 layouts 也保持为空。随后测试手动注册 raw 与 custom 两个 tensor，仍然传空描述符。
消费者必须拿到原 tensor 字典和空 layouts，不能根据 rank、层名或 spec 自动猜 BHNC。要注意这个用例本身没有真正分配 HiSparse raw storage：它验证空分配输出和“外部提供 tensor 可以无声明注册”。下一项 hybrid 测试才实际走到 raw-storage 分支，并检查 raw 没有被生成描述符。

7. hybrid 不是一个全模型的 layout 字符串：要检查每个实际 view。
test_hybrid_allocator_registers_each_created_view 把 full attention、sliding attention、Mamba 和 HiSparse raw 四种 spec 放进同一配置。所有 KVCacheTensor 的 size 都是整块 backing storage 的总字节数，offset 则逐段推进；因此这些 view 共用 allocation，但访问不同区域。


层实际 shape测试中的含义
full(2,2,4,4)float32；2 heads、4 states，CONTENT=4。
sliding(2,1,2,4)float16；1 head、2 states，同一组轴角色不代表相同几何。
mamba(2,1,1,24)每块 24 字节的不透明状态：(2 + 2×2) × 4；HEAD/STATE 是大小为 1 的 slot。
raw一维 backing buffer没有 layer view，不应生成 tensor layout。


关键断言有三组：layouts 的 key 恰好是 full/sliding/mamba；三层的轴都为 (BLOCK,HEAD,STATE,CONTENT)；逐层写入不同值后，注册消费者能读到各自的数据，并且三层的 untyped_storage().data_ptr() 都等于 raw 的 storage 地址。这同时约束了“每层声明”和“共用 backing”的关系。
代码只对 full/sliding 显式断言 dtype，对 Mamba 的 24 字节 shape 和值做检查；它没有把 Mamba 的两份 float32 状态解码回来，更没有证明 state 和 token 的推进比例。这些信息仍属于 spec 和实际执行逻辑。

def test_hybrid_allocator_registers_each_created_view(make_connector):
    """Hybrid specs share axis roles, not shapes, dtype or content encoding."""
    specs = {
        "full": FullAttentionSpec(
            block_size=4, num_kv_heads=2, head_size=2, dtype=torch.float32
        ),
        "sliding": SlidingWindowSpec(
            block_size=2,
            num_kv_heads=1,
            head_size=2,
            dtype=torch.float16,
            sliding_window=8,
        ),
        "mamba": MambaSpec(
            block_size=4,
            shapes=((2,), (2, 2)),
            dtypes=(torch.float32, torch.float32),
        ),
        "raw": HiSparseResidentSpec(block_size=4, page_size=64),
    }
    num_blocks = 2
    size = sum(num_blocks * spec.page_size_bytes for spec in specs.values())
    tensors = []
    offset = 0
    for name, spec in specs.items():
        tensors.append(
            KVCacheTensor(
                size=size,
                layers=[name],
                offset=offset,
                layer_stride=num_blocks * spec.page_size_bytes,
                block_stride=spec.page_size_bytes,
            )
        )
        offset += num_blocks * spec.page_size_bytes
    config = KVCacheConfig(
        num_blocks,
        tensors,
        [KVCacheGroupSpec([name], spec) for name, spec in specs.items()],
    )
    layouts: dict[str, KVCacheTensorLayout] = {}
    caches = allocate_kv_cache(
        config, torch.device("cpu"), KVCacheLayout.LBHNC, tensor_layouts=layouts
    )
    assert set(layouts) == {"full", "sliding", "mamba"}
    assert caches["full"].shape == (2, 2, 4, 4)
    assert caches["sliding"].shape == (2, 1, 2, 4)
    assert caches["mamba"].shape == (2, 1, 1, 24)
    assert caches["raw"].ndim == 1
    assert caches["full"].dtype == torch.float32
    assert caches["sliding"].dtype == torch.float16
    for value, name in enumerate(layouts, start=1):
        caches[name].fill_(value)
    connector = make_connector(config)
    connector.register_kv_caches_with_layouts(caches, layouts)
    consumer = connector.sub_connectors[1]
    assert isinstance(consumer, AxisRegistrationConnector)
    for value, name in enumerate(layouts, start=1):
        axes = consumer.layouts[name]
        assert axes.axes == (Axis.BLOCK, Axis.HEAD, Axis.STATE, Axis.CONTENT)
        assert torch.all(consumer.registered_caches[name] == value)
        assert consumer.registered_caches[name].untyped_storage().data_ptr() == (
            caches["raw"].untyped_storage().data_ptr()
        )
这份测试证明到哪一步？ CPU 上的真实 allocator → view metadata → MultiConnector → 测试消费者，以及错误路径。它没有运行 MRV1/MRV2 的完整 initialize_kv_cache、HiSparse host/device 绑定、attention kernel、模型 serving 或 LMCache IPC。原始 RBLN 用例也不是 rebel SDK 测试。7 个函数经参数化得到 17 个 pytest 用例；offset 循环和逐层循环是同一个用例里的额外断言，不应再加进用例数。
