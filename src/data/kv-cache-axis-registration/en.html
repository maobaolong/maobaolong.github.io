Declare axis meaning at the point of creation.

A tensor supplies geometry. It does not label its dimensions. The new registration hook carries a separate, typed declaration of those labels.

What is added

KVCacheAxis, KVCacheTensorLayout, an optional registration hook, standard view declarations, runner propagation and MultiConnector forwarding.

What stays authoritative

The actual tensor's shape, strides, dtype and storage offset. Cache specs own content encoding and state granularity.

What is not completed

Hardware-plugin adoption, LMCache consumption, a versioned MP schema, arbitrary component roles, or conversion between incompatible encodings.

Scope: registration-time metadata. This PR does not transpose tensors, change attention kernels, or claim a throughput improvement.

02 / The motivating correctness problem

At two blocks, shape and strides cannot tell K from V.

RBLN has two legitimate views: custom kernels use [B,2,H,1,N,D]; the Triton path uses [2,B,H,1,N,D]. When B=2, the shape and contiguous strides are identical. A detector can choose an interpretation, but cannot recover the producer's intent.

Figure 2 · Interactive ambiguity, using the same physical values
Identical shape and strides

Illustration: H=1, N=2, D=1; scalar values are physical offsets. Color means the declared component, not information stored in the bytes.

Blocks first

BLOCKKVHEAD1STATEHEAD_DIM

K/V first

KVBLOCKHEAD1STATEHEAD_DIM

Canonical output is independently ordered by component, then block and state. At B=2, identical input geometry produces different K/V sequences. At B=3 these two shapes differ, but that does not turn arbitrary shapes into semantic declarations.

Why round-trip tests can miss this: saving with the wrong interpretation and restoring with the same wrong interpretation may reconstruct the original buffer. Comparing independently expected K and V sequences catches the semantic error.

LMCache #5748 adds support for both RBLN formats and addresses a concrete deployment regression. The two-block ambiguity explains why a durable producer contract is still valuable after that detector fix.

04 / Same axis roles, different memory order

The standard view stays BHNC. Its strides can change.

The common allocator creates a logical [L,B,H,N,C] view, then selects each layer to expose [B,H,N,C]. Physical permutations and page padding are expressed through strides and offsets, not by relabeling the public indices.

LBHNC[8,4,16,128][8192,2048,128,1](BLOCK,HEAD,STATE,CONTENT)

The small colored strips are illustrative H/N cells; the numeric table uses B=8, H=4, N=16, C=128. Neither strip implies that all backends support both orders.

address(b,h,n,c) = storage_base + element_size × (
    storage_offset + b·stride_B + h·stride_H + n·stride_N + c·stride_C
)

Tensor strides and storage_offset are in elements; allocator planning may use byte strides. Convert units explicitly. Axis metadata supplies the meaning of B/H/N/C, not the numbers in this address formula.

What does HiSparse do?


HiSparse is an experimental, local sparse-MLA KV offload scheme. Sparse attention selects a subset of historical positions per step. HiSparse can keep historical KV in pinned host memory while the GPU uses resident pages and a hot-row cache, reducing the historical KV footprint on the GPU at the cost of host memory and transfers.


top-k historical positions selected for this step
                ↓
GPU resident page hit? ── yes → use the resident row
                ↓ no
GPU hot-row hit? ──────── yes → use the cached row
                ↓ no
fetch the pinned host row into the GPU hot cache


The fused GPU resolver checks resident pages, then hot rows, then host memory. HiSparse's indexer KV is managed separately; HiSparse does not automatically create its own host copy of every KV group in the model.


How is HiSparse enabled?


Configuring HiSparseConnector, directly or through MultiConnector, infers default hisparse_config. The connector supplies the host_pool_gib capacity; HiSparseConfig tunes fields such as the GPU hot-buffer size. A complete, supported configuration is required. Low free GPU memory alone does not activate HiSparse.


Snapshot constraints: NVIDIA CUDA, MRV2, and DSA models with index_topk. Pipeline parallelism and decode context parallelism are unsupported. The single cudagraph_mode=FULL setting is rejected; FULL_AND_PIECEWISE, the default, can still capture full decode graphs. These are compatibility conditions, not hardware validation performed by this PR.


HiSparseConnector manages local host/GPU residency. It can be composed with P/D or another offload connector through MultiConnector. This role is distinct from the remaining LMCache adapter/MP integration described later.


Why this matters to #63699: normal MRV2 allocation and the HiSparse host/device path must both carry matching declarations for the actual registered views. The PR propagates metadata through those paths; it does not choose the runner or enable HiSparse. Existing allocator return types remain unchanged, shared layers inherit their target descriptor, and raw buffers are not assigned a fabricated BHNC declaration.

10 / A size-one dimension is not automatically a KV dimension
MLA has no separate K/V selector in its standard view.


The descriptor's KV role means two separately addressable components, K then V. MLA's shared latent representation does not become a one-element K/V selector. MLAAttentionSpec sets head_size_v=0; its content is interpreted through the spec.


Figure 10 · Three valid MLA declarations
Standard view
[B,1,N,C]
BLOCKHEADSTATECONTENT
Size one is a head slot. Keep its semantic role.
Custom squeezed view
[B,N,C]
BLOCKSTATECONTENT
No head or K/V axis is required by the descriptor.
Custom padded rank
[1,B,N,C]
SINGLETONBLOCKSTATECONTENT
Use SINGLETON for an actual placeholder, not a semantic axis.


Invalid declaration: describing [1,B,N,C] as (KV,BLOCK,STATE,CONTENT) raises ValueError. A lone element does not identify K, V or latent content. Relaxing the size check would introduce ambiguity rather than encode MLA.


validate_shape checks rank, KV size two and SINGLETON size one. Construction rejects duplicate named roles except SINGLETON. These checks do not prove a declaration is true: equal-sized axes can still be mislabeled. Correctness starts with the producer's known view contract.

13 / What is lost when the declaration is absent
A wrong axis interpretation can become a wrong byte selection.


Figure 13 · A possible failure chain, not a claimed production incident
Unlabeled viewConsumer sees shape and strides.
→
Ambiguous detectorTwo supported interpretations fit.
→
Wrong geometryBlock/KV role or component split is wrong.
→
Wrong bytes transferredCanonical chunks can contain mismatched K/V sequences.


Visible rejection
A new producer layout may be refused as unsupported. RBLN blocks-first support in LMCache #5748 addresses such a concrete integration regression.
Silent ambiguity
Equal-sized axes can pass shape and bounds checks. Canonical-value tests demonstrate the risk; this guide does not claim an observed production output failure.
Maintenance coupling
Every producer shape change can require a new consumer heuristic, even though the producer already knows the intended interpretation.


Not every tensor-only integration is unsafe. Existing spec-aware contracts can be precise, and many layouts are unambiguous. The issue is treating geometry or backend names as a complete semantic contract when they are not.

14 / Metadata must follow the view's lifecycle

16 / A practical review route
Review the contract before the plumbing.


  1. 1. Types and validation. Is the distinction between KV selector, HEAD, STATE and opaque CONTENT clear? Does validation reject impossible fixed-size axes without pretending to prove semantics?
  2. 2. View creation. Are declarations attached where the actual BHNC view is created? Are raw-storage paths omitted?
  3. 3. Runner propagation. Follow the fresh output map through standard/HiSparse allocation and shared aliases. Verify registration describes the connector view.
  4. 4. Compatibility. Does inherited registration preserve existing overrides? Does MultiConnector pass the same semantics to all children?
  5. 5. Behavior tests. Compare independently expected K/V values, tensor identity, strides, mixed specs, aliases and error handling.
  6. 6. Downstream boundary. Check that RBLN uses the shared upstream contract, while LMCache consumer/MP work remains explicitly out of scope.

def test_two_blocks_keep_kv_semantics_through_mixed_connectors(
    make_connector, axes, expected
):
    """Equal shapes must still give the consumer the producer's K/V values."""
    connector = make_connector(KVCacheConfig(2, [], []))
    layout = KVCacheTensorLayout(
        (*axes, Axis.HEAD, Axis.SINGLETON, Axis.STATE, Axis.HEAD_DIM)
    )
    order = (Axis.KV, Axis.BLOCK, Axis.STATE, Axis.HEAD, Axis.HEAD_DIM, Axis.SINGLETON)
    for offset in (0, 100):

        assert isinstance(consumer, AxisRegistrationConnector)

        canonical = consumer.registered_caches["layer"].permute(
            *(consumer.layouts["layer"].axis_index(axis) for axis in order)
        )
        assert canonical.flatten().tolist() == [value + offset for value in expected]
2. Do allocator views retain their values across physical layouts and aliases?
test_allocator_views_and_aliases_keep_their_values expands into eight cases: all six KVCacheLayout members, plus padded LBHNC and BLHNC. It calls the real compute_layout_strides and allocate_kv_cache; allocation results are not mocked. Two layers share a backing allocation while exposing separate views.


The test writes 0…63 into first, fills second with -1, and aliases first. The consumer constructs semantic coordinates B=1,H=0,N=2,C=3 from the received axis tuple. In logical shape (2,2,4,4), the expected value is (((1×2+0)×4+2)×4+3)=43, independent of physical order. A descriptor/view mismatch can therefore produce a concrete wrong value.


It also verifies that second was not overwritten and that stride(0) × element_size() matches the configured block stride in bytes. A padded page is 144 bytes rather than 128, checking that registration preserves gaps between pages. Only block stride has an explicit equality assertion; layer stride participates in construction but is not separately asserted. The test manually attaches both the alias tensor and descriptor. It verifies forwarding after attachment, not automatic alias wiring inside either model runner.

@pytest.mark.parametrize(
    ("physical_layout", "padded"),
    [(layout, False) for layout in KVCacheLayout]
    + [(KVCacheLayout.LBHNC, True), (KVCacheLayout.BLHNC, True)],
)
def test_allocator_views_and_aliases_keep_their_values(
    make_connector, physical_layout, padded
):
    """Registration describes indexing order while preserving real strides."""
    spec = FullAttentionSpec(
        block_size=4,
        num_kv_heads=2,
        head_size=2,
        dtype=torch.float32,
        page_size_padded=144 if padded else None,
    )
    nb, nl = 2, 2
    strides = compute_layout_strides(spec, nb, nl, physical_layout)
    config = KVCacheConfig(
        num_blocks=nb,
        kv_cache_tensors=[
            KVCacheTensor(
                size=nb * nl * spec.page_size_bytes,
                layers=["first", "second"],
                layer_stride=strides[0],
                block_stride=strides[1],
            )
        ],
        kv_cache_groups=[
            KVCacheGroupSpec(
                ["first", "second"],
                UniformTypeKVCacheSpecs(
                    block_size=4, kv_cache_specs={"first": spec, "second": spec}
                ),
            )
        ],
    )
    layouts: dict[str, KVCacheTensorLayout] = {}
    caches = allocate_kv_cache(
        config, torch.device("cpu"), physical_layout, tensor_layouts=layouts
    )
    caches["first"].copy_(torch.arange(64).reshape(2, 2, 4, 4))
    caches["second"].fill_(-1)
    add_kv_sharing_layers_to_kv_cache_groups({"alias": "first"}, config.kv_cache_groups)
    caches["alias"] = caches["first"]
    layouts["alias"] = layouts["first"]
    connector = make_connector(config)
    connector.register_kv_caches_with_layouts(caches, layouts)
    consumer = connector.sub_connectors[1]
    assert isinstance(consumer, AxisRegistrationConnector)
    assert consumer.registered_caches is caches
    assert set(consumer.layouts) == set(caches)
    assert consumer.layouts["alias"] == consumer.layouts["first"]
    layout = consumer.layouts["first"]
    index = tuple(
        {Axis.BLOCK: 1, Axis.HEAD: 0, Axis.STATE: 2, Axis.CONTENT: 3}[axis]
        for axis in layout.axes
    )
    assert consumer.registered_caches["alias"][index].item() == 43
    assert torch.all(caches["second"] == -1)
    assert caches["first"].stride(0) * caches["first"].element_size() == strides[1]

7. Hybrid caches require declarations for each actual view, not one model-wide string.
test_hybrid_allocator_registers_each_created_view combines full attention, sliding attention, Mamba and HiSparse raw specs. Each KVCacheTensor uses the total backing allocation size, while its offset advances through separate regions. The resulting views share an allocation without addressing the same region.


LayerActual shapeMeaning in this test
full(2,2,4,4)float32; 2 heads, 4 states, CONTENT width 4.
sliding(2,1,2,4)float16; 1 head and 2 states. Shared roles do not imply shared geometry.
mamba(2,1,1,24)24 opaque state bytes per block: (2 + 2×2) × 4. HEAD/STATE are size-one slots.
rawOne-dimensional backing bufferNo layer view, so no tensor-axis declaration.


The assertions check three things: only full/sliding/mamba have descriptor keys; all three declare (BLOCK,HEAD,STATE,CONTENT); and separately written layer values survive registration while each layer's untyped_storage().data_ptr() equals raw's storage address. This connects per-view declarations with a shared backing allocation.
Only full and sliding have explicit dtype assertions. Mamba's byte-shaped view and values are checked, but the two float32 state components are not decoded. Nor does the test establish state-to-token granularity; that still belongs to the spec and execution logic.

def test_hybrid_allocator_registers_each_created_view(make_connector):
    """Hybrid specs share axis roles, not shapes, dtype or content encoding."""
    specs = {
        "full": FullAttentionSpec(
            block_size=4, num_kv_heads=2, head_size=2, dtype=torch.float32
        ),
        "sliding": SlidingWindowSpec(
            block_size=2,
            num_kv_heads=1,
            head_size=2,
            dtype=torch.float16,
            sliding_window=8,
        ),
        "mamba": MambaSpec(
            block_size=4,
            shapes=((2,), (2, 2)),
            dtypes=(torch.float32, torch.float32),
        ),
        "raw": HiSparseResidentSpec(block_size=4, page_size=64),
    }
    num_blocks = 2
    size = sum(num_blocks * spec.page_size_bytes for spec in specs.values())
    tensors = []
    offset = 0
    for name, spec in specs.items():
        tensors.append(
            KVCacheTensor(
                size=size,
                layers=[name],
                offset=offset,
                layer_stride=num_blocks * spec.page_size_bytes,
                block_stride=spec.page_size_bytes,
            )
        )
        offset += num_blocks * spec.page_size_bytes
    config = KVCacheConfig(
        num_blocks,
        tensors,
        [KVCacheGroupSpec([name], spec) for name, spec in specs.items()],
    )
    layouts: dict[str, KVCacheTensorLayout] = {}
    caches = allocate_kv_cache(
        config, torch.device("cpu"), KVCacheLayout.LBHNC, tensor_layouts=layouts
    )
    assert set(layouts) == {"full", "sliding", "mamba"}
    assert caches["full"].shape == (2, 2, 4, 4)
    assert caches["sliding"].shape == (2, 1, 2, 4)
    assert caches["mamba"].shape == (2, 1, 1, 24)
    assert caches["raw"].ndim == 1
    assert caches["full"].dtype == torch.float32
    assert caches["sliding"].dtype == torch.float16
    for value, name in enumerate(layouts, start=1):
        caches[name].fill_(value)
    connector = make_connector(config)
    connector.register_kv_caches_with_layouts(caches, layouts)
    consumer = connector.sub_connectors[1]
    assert isinstance(consumer, AxisRegistrationConnector)
    for value, name in enumerate(layouts, start=1):
        axes = consumer.layouts[name]
        assert axes.axes == (Axis.BLOCK, Axis.HEAD, Axis.STATE, Axis.CONTENT)
        assert torch.all(consumer.registered_caches[name] == value)
        assert consumer.registered_caches[name].untyped_storage().data_ptr() == (
            caches["raw"].untyped_storage().data_ptr()
        )
