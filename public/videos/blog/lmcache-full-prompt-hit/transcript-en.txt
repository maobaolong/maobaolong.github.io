You send the exact same prompt twice. On the second request, LMCache finds all two hundred and fifty-seven tokens. But vLLM plans to load only two hundred and fifty-six. Why leave one out? Start with how a model generates its first output token.

The model splits your text into tokens, then processes the input. That's prefill. At the last input position, the model produces a score for every candidate in its vocabulary. Those scores are called logits. vLLM uses them to pick the first output token.

The KV cache holds a different piece of the computation. Think of it as notes that each attention layer takes while reading the prompt. At a new position, the layer can look back at those notes. If a new request starts with the same tokens, the model can reuse the notes and skip that earlier work. The notes don't contain the logits. To get those, the model can run the last prompt token again, using the earlier KV.

Now let's repeat a request. The first time, LMCache saves one chunk of two hundred and fifty-six tokens and a one-token tail. Then we clear just vLLM's local prefix cache and send the same prompt again. The local cache misses. LMCache still has all two hundred and fifty-seven tokens. The plan is to load the first two hundred and fifty-six and run the last one in the next forward pass.

Here's where the lengths get out of sync. The scheduler gives the load enough GPU blocks for one full chunk. But retrieve still looks up objects for the original two hundred and fifty-seven tokens. The full chunk has a destination. The tail has none. When the tail handler asks for a GPU block, it throws, and the whole retrieval fails.

Zoom in on the boundary. A chunk holds two hundred and fifty-six tokens. A GPU block holds sixty-four. When the prompt is exactly two hundred and fifty-six tokens, we reserve the last one. Loading the first two hundred and fifty-five still takes four blocks. At five hundred and twelve, the load plan ends at five hundred and eleven. That still takes eight blocks. Neither aligned length has a tail object. At two hundred and fifty-seven, the tail has just one token. That's the one reserved for forward. Add one more token, and the prompt is two hundred and fifty-eight. We reserve the last one, and token two hundred and fifty-seven still needs its KV loaded. That one extra position requires a fifth block. Only a one-token tail can be stored yet have no destination in this load plan.

Now turn off save unfull chunk. With the local cache still empty in our example, the two hundred and fifty-seven and two hundred and fifty-eight token prompts both hit only the first full chunk. Lookup stops at two hundred and fifty-six. Both loads use four blocks. One request runs one token from there, and the other runs two. The full chunk is still reused, and retrieve has no tail to handle. An aligned prompt of two hundred and fifty-six or five hundred and twelve can still hit in full, with the last token reserved for forward.

The pull request adds a check inside retrieve. If the tail object exists and every group has an empty list of destination blocks for it, skip the tail and keep the full chunks. If some groups have blocks and others don't, the existing check still raises. The token count also leaves out the skipped tail.

So when you see a full hit, ask three questions. How much was stored? How much are we loading? And what still runs? Here it's two hundred and fifty-seven, two hundred and fifty-six, and that very last token. Once the load succeeds, the forward pass produces the logits and generation can begin.
