[00:01:02.979] 02 谁在搬数据 / 普通读取：经过主机中转
普通读取常见的路径，是先把固态硬盘的数据放进主机内存，再复制到显存。这里的主机内存，是数据中转站。直接存储要省掉的，正是这一步中转。

[00:09:26.951] 06 STORE：从分页 KV 到 SSD / 为什么不能直接写引擎的 KV 页？
为什么不让硬盘直接读取引擎那些页？因为存储接口处理连续地址和长度，不理解词元、层和块编号。临时显存同时解决布局转换、成批读写和注册生命周期，把引擎布局与存储接口分开。

数据整理好之后，存储上下文根据显存切片，找到注册基址和区内偏移；再结合缓存对象的存储池偏移，确定写多少、从哪儿读、写到哪儿。跨注册区时，就拆成多笔提交。

[00:10:20.167] 06 STORE：从分页 KV 到 SSD / handle.write_async() 提交原生写入
句柄对象随后调用具体后端的异步写入。前面的收集操作和这里的写入，在传输执行流上有顺序，所以存储设备不会抢先读取还没整理好的临时显存。

[00:10:35.167] 06 STORE：从分页 KV 到 SSD / 完成后发布缓存，并允许资源复用
写入完成之后，事件和回调衔接收尾流程，存储管理器完成写入状态的更新。这时，缓存对象才完成发布，相关缓冲区才能按约定复用。函数已经返回，与设备已经写完，是两回事。

[00:10:53.930] 07 RETRIEVE：从 SSD 回到分页 KV / retrieve()：找到缓存与本次目标块
取回时，先找到命中的缓存，以及这一次请求的目标块编号。目标块可能和上一次完全不同，所以不能把保存时的物理地址，直接拿来当恢复位置。

[00:11:07.847] 07 RETRIEVE：从 SSD 回到分页 KV / 锁住命中对象，避免读取中被淘汰
存储管理器交出预取结果，并在读取期间保留这些对象，避免字节还没搬完，缓存位置就被淘汰或复用。执行流也会建立与生产者的依赖关系。

[00:11:22.229] 07 RETRIEVE：从 SSD 回到分页 KV / 先读到已注册的连续 GPU buffer
然后，句柄提交异步读取，把存储池中的连续字节，送进已经注册的临时显存。硬盘只需要认识地址、偏移和长度，不需要知道这些字节属于哪一层注意力。

[00:11:37.680] 07 RETRIEVE：从 SSD 回到分页 KV / 再 scatter：按本次 block IDs 写回
等读取在执行流上完成，布局搬运内核再把临时显存里的数据，分散写入这一次的目标块。图中逻辑顺序没有改变，但实际块编号，已经换成了新的位置。

[00:11:52.525] 07 RETRIEVE：从 SSD 回到分页 KV / 为什么读取也不能直接落到最终位置？
这就是读取同样需要临时显存的原因。连续存储字节与引擎分页布局之间，需要一次明确的转换。搬运还要遵守对象分组和需要跳过的范围，避免覆盖应保留的词元。

[00:12:08.724] 07 RETRIEVE：从 SSD 回到分页 KV / 完成事件之后，才能消费并释放保护
最后，完成事件告诉后续工作，目标缓存已经准备好；读取收尾流程再释放对象保护。不能刚把读命令发出去，就让模型使用尚未到达的数据，也不能提前让存储区域被覆盖。

[00:12:25.992] 08 async：谁在等谁 / 异步返回，只表示提交完成

[00:12:42.255] 08 async：谁在等谁 / 同一 stream 保证顺序，不保证并行
保存时，顺序是先收集，再写盘，再记录完成事件。取回时，是先读盘，再分散写回，再记录事件。有序不等于并行，异步也不是自动让所有步骤同时发生。

[00:12:58.569] 08 async：谁在等谁 / Submission：参数也必须活到调用结束

[00:13:16.352] 08 async：谁在等谁 / 完成事件、I/O 成功、持久化不是一回事
当前实现用检查点回收已经完成的提交记录，但这不等于逐笔核验实际传输字节数。执行完成、读写成功、数据已经持久化，是不同层次的问题，不能只凭一个事件就混为一谈。

[00:15:31.784] 10 回到 GDS 的价值 / 留下更多 KV，减少重复计算
